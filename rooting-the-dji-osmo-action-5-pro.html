Rooting the DJI Osmo Action 5 Pro

November 4th, 2026

We rooted a DJI Osmo Action 5 Pro using a Qualcomm engineering cable bought on Taobao. After two small partition changes, connecting the camera over USB gives us a Linux root shell with adb shell. No replacement operating system, modified system image, or borrowed userdata image was needed.

Credit for the method goes to Alliot's Chinese-language post, OSMO Action5Pro 解锁BL并开启adbd ("Unlocking the Osmo Action 5 Pro bootloader and enabling adbd"). This is an English walkthrough of that procedure, written from our own run on Linux, with an additional complication: Alliot's tested camera used slot A; ours used slot B. We initially stopped there, investigated, and eventually completed the procedure without switching slots.

This writes bootloader-related partitions directly. Incorrect addresses, incompatible images, or interrupted power can leave the camera unable to boot. Unlocking may erase data or affect warranty coverage. What follows worked on one camera with the versions below; it is not a claim that every Action 5 Pro or firmware revision is compatible.

What we tested

Platform Qualcomm QCS8550 / SM8550 family, Kalama

The camera firmware version matches Alliot's tested version. The two version fields are different: check both in Settings → Device Info. If the camera is stuck on the USB connected screen, unplug it briefly to reach settings. A blank screen in Qualcomm EDL mode, on the other hand, is expected.

What the root method changes

The camera already contains /sbin/adbd, its launch script, USB gadget support, and an enabled adbd.service. Alliot's method makes that existing software accessible by changing two things:

  1. Patch two bytes in this camera's devinfo partition, setting the bootloader's unlocked and critical-unlocked flags.
  2. Replace the active slot's ABL, the Android Boot Loader, with a known factory ABL. This lets the camera boot in engineering mode and expose root ADB.

The resulting kernel command line includes mp_state=engineering and androidboot.secure_debug=1. We left system, userdata, GPT, XBL, calibration partitions, and the inactive ABL untouched. In particular, do not flash someone else's userdata image: it can overwrite device-specific settings, credentials, and identity data.

The cable

We bought a second-generation Qualcomm 9008 engineering cable on Taobao, with a USB-C connector and an EDL button. The useful Chinese search term is 高通二代工程线 9008 Type-C. An ordinary USB-C data cable doesn't provide that button-triggered entry into EDL.

For English-speaking readers, there is an eBay listing advertised as an EDL 9008 engineering cable v2.0. We have not tested that seller's cable; the tested cable came from Taobao. Check the connector and generation rather than assuming every product labeled "EDL" is equivalent. If you would prefer to buy a cable from us, email me and we can arrange one.

1. Get the tools and verify the images

We used bkerler's EDL client at Alliot's pinned commit. These commands use Bash in a dedicated working directory. On Ubuntu, install Python with venv support, Git, libusb, unzip, ADB, and Fastboot first. 

set -euo pipefail
mkdir action5-root
cd action5-root

python3 -m venv .edl-venv
git clone https://github.com/bkerler/edl.git edl-tool
git -C edl-tool checkout 2f8e89a848afaaef68997fcbcb5b178d958d497b
.edl-venv/bin/pip install ./edl-tool

curl -fL https://github.com/AlliotTech/action-control/releases/download/action5pro-unlock-files.zip/action5pro-unlock-files.zip \
  -o action5pro-unlock-files.zip
unzip action5pro-unlock-files.zip

sha256sum loader/RedMagicCommon_8Gen2_devprg img-unlock/abl-factory.img
wc -c img-unlock/abl-factory.img

The expected SHA-256 hashes are:

b85fb0e651f88f12e3c9b7b56c0f7229449c410f87fc20c6bc35698516383297  loader/RedMagicCommon_8Gen2_devprg
658af73f3319af4c07c733fe6ad184f68c299b678819815bbdacbaaff3b12466  img-unlock/abl-factory.img

The factory ABL must be exactly 1048576 bytes. Stop if either hash or the size differs. The loader's RedMagic name looks surprising, but this exact programmer is the one Alliot tested on the shared Qualcomm platform and the one we successfully used. That does not make arbitrary programmers for the same SoC interchangeable.

Define a helper without hiding which operations access storage:

EDL_PY="$PWD/.edl-venv/bin/python"
EDL_SCRIPT="$PWD/edl-tool/edl.py"
LOADER="$PWD/loader/RedMagicCommon_8Gen2_devprg"
FACTORY_ABL="$PWD/img-unlock/abl-factory.img"
BACKUP="$PWD/backup-original"

edl() {
  "$EDL_PY" "$EDL_SCRIPT" "$@" --loader="$LOADER"
}

The client needs permission to access the USB device. On Linux, use suitable udev rules or run it with the required privileges. We also temporarily stopped ModemManager with sudo systemctl stop ModemManager so it would not probe the Qualcomm device, and restarted it when finished. An optional Capstone or Keystone warning from the client is not itself a Firehose connection failure.

2. Enter EDL and read the partition table

  1. Power off the camera and unplug USB. Unmount any camera storage on the host before unplugging.
  2. Remove the battery.
  3. Hold the engineering cable's button while plugging it into the camera.
  4. Confirm that lsusb shows 05c6:9008, then release the button.
  5. Reinstall the battery before continuing, leaving the cable attached.

The screen stays blank in EDL. Neither ADB nor Fastboot is supposed to see a device in this mode. USB identification is the useful check: 

lsusb -d 05c6:9008
edl printgpt --memory=ufs | tee gpt-before.log

This uploads the programmer into RAM and reads the GPTs. On our camera, Firehose reported UFS, 4096-byte logical blocks, and six LUNs. Its partition table showed the following locations. The sector numbers are decimal and refer to 4096-byte blocks, not 512-byte sectors.

Partition LUN Start sector Sectors Active
devinfo 4 239752 1 Shared
abl_a 4 66566 256 No
abl_b 4 190279 256 Yes
userdata 0 15214715 25472 Shared

Those are observations from our device, not universal flash addresses. Read your own GPT, confirm the model, block size, partition sizes, and active slot, and derive addresses from that. If anything is unexpected, stop and investigate before writing.

The slot B roadblock

Alliot explicitly says to stop if slot B is active. We did stop initially: mechanically replacing every "A" with "B" would skip the main question, whether the factory image actually selects and boots slot B correctly. Switching to A merely to match the tutorial could also boot older firmware.

We backed up both ABLs and the active system image, decompressed the factory and stock B ABL payloads, and inspected the ARM64 PE code with Capstone. After resolving relocated string addresses, the checked multi-slot detection, active-slot selection, and slot-attribute routines matched. Both images contained the UTF-16 suffix table _a, _b; the selection code inspected GPT active and priority bits, rather than simply forcing A. The boot code also constructed the kernel's slot suffix.

That was evidence for an adaptation, not a complete compatibility proof. Combined with the matching camera firmware and fresh, unchanged partition reads, it gave us a basis for a staged test. We retained B, patched only devinfo first, verified a normal boot, and only then replaced abl_b. The successful boot and later Fastboot checks are the on-device evidence. Slot B support here is our additional test result, not something Alliot's original post promised.

3. Back up this camera

Save the small partitions and GPT images before touching anything. The following command skips the large data partitions: 

mkdir -p "$BACKUP"
edl rl "$BACKUP" --memory=ufs \
  --skip=system_a,system_b,emulated,userdata,blackbox,blackbox_upgrade,rawdump

test -f "$BACKUP/lun4/devinfo.bin"
test -f "$BACKUP/lun4/abl_a.bin"
test -f "$BACKUP/lun4/abl_b.bin"

The lun4 paths above describe our layout; adjust them only after inspecting your own. We separately read the entire userdata partition and the active system_b image. This was not a full media backup: internal media, the SD card, blackbox data, and the inactive system image were not included. Copy any recordings you care about separately.

In the remaining commands, set DEVINFO_LUN, DEVINFO_START, DEVINFO_SECTORS, ABL_LUN, ABL_START, and ABL_SECTORS from your own GPT. ORIGINAL_DEVINFO and ORIGINAL_ABL must point to this camera's original backup files, with the latter matching the active slot. We used the B entry in the table, not the A entry. Likewise, derive the userdata variables before reading it: 

mkdir -p "$BACKUP/lun$USERDATA_LUN"
edl rs "$USERDATA_START" "$USERDATA_SECTORS" \
  "$BACKUP/lun$USERDATA_LUN/userdata.bin" \
  --memory=ufs --lun="$USERDATA_LUN"

(cd "$BACKUP" && sha256sum lun*/*.bin > SHA256SUMS)
(cd "$BACKUP" && sha256sum -c SHA256SUMS)

Check every backup's size against GPT, and verify the hashes again after copying it. We also checked all six primary GPT header and partition-array CRCs. We made a second verified copy in another directory, but both copies were on the same host SSD. That protects against accidentally overwriting one directory, not SSD failure; a separate disk is a better backup target. Keep device-specific backups private.

4. Unlock two flags, then test a normal boot

First, read the live devinfo and active ABL again and compare them with their backups. Any unexpected difference needs an explanation before proceeding: 

edl rs "$DEVINFO_START" "$DEVINFO_SECTORS" devinfo-before.bin \
  --memory=ufs --lun="$DEVINFO_LUN"
cmp devinfo-before.bin "$ORIGINAL_DEVINFO"

edl rs "$ABL_START" "$ABL_SECTORS" abl-before.bin \
  --memory=ufs --lun="$ABL_LUN"
cmp abl-before.bin "$ORIGINAL_ABL"

Generate a patched copy from this camera's devinfo. The expected image is 4096 bytes, starts with ANDROID-BOOT!, and has zero at offsets 0x10 and 0x18. Unexpected input means stop, not "patch it anyway." 

python3 - "$ORIGINAL_DEVINFO" devinfo-unlocked.bin <<'PY'
from pathlib import Path
import sys

src, dst = map(Path, sys.argv[1:])
original = src.read_bytes()
assert len(original) == 4096
assert original.startswith(b"ANDROID-BOOT!")
assert original[0x10] == original[0x18] == 0

patched = bytearray(original)
patched[0x10] = patched[0x18] = 1
assert [i for i, (a, b) in enumerate(zip(original, patched)) if a != b] == [0x10, 0x18]
dst.write_bytes(patched)
PY

# First persistent write: one devinfo sector, with only two bytes changed.
edl ws "$DEVINFO_START" devinfo-unlocked.bin --memory=ufs --lun="$DEVINFO_LUN"
edl rs "$DEVINFO_START" "$DEVINFO_SECTORS" devinfo-after.bin \
  --memory=ufs --lun="$DEVINFO_LUN"
cmp devinfo-after.bin devinfo-unlocked.bin

# Only reset after the complete readback matches.
edl reset --resetmode=reset

Our reset command printed a USB input/output error as the camera disconnected. We confirmed that the 9008 device disappeared rather than treating the message alone as a failed write. If it stays in EDL, or the readback fails, investigate before proceeding. If it remains powered off, press the power button. We unplugged USB to leave the connected screen and confirmed that the live view and touch controls still worked. At this stage the ABL is still original; root ADB was not yet available.

5. Replace only the active ABL

Repeat the physical EDL entry procedure and reinstall the battery. Re-read GPT and verify that the layout and active slot are unchanged. Read devinfo and the active ABL again: devinfo must match the unlocked image, while ABL must still match the original backup. Recheck the factory ABL's fixed hash and 1 MiB size before writing. 

edl printgpt --memory=ufs | tee gpt-second-stage.log
edl rs "$DEVINFO_START" "$DEVINFO_SECTORS" devinfo-second-stage.bin \
  --memory=ufs --lun="$DEVINFO_LUN"
cmp devinfo-second-stage.bin devinfo-unlocked.bin

edl rs "$ABL_START" "$ABL_SECTORS" abl-second-stage.bin \
  --memory=ufs --lun="$ABL_LUN"
cmp abl-second-stage.bin "$ORIGINAL_ABL"

edl ws "$ABL_START" "$FACTORY_ABL" --memory=ufs --lun="$ABL_LUN"
edl rs "$ABL_START" "$ABL_SECTORS" abl-after.bin \
  --memory=ufs --lun="$ABL_LUN"
cmp abl-after.bin "$FACTORY_ABL"
sha256sum abl-after.bin "$FACTORY_ABL"

# Again, only after a byte-for-byte match:
edl reset --resetmode=reset

In our run, this wrote only abl_b, at its freshly verified location. We did not switch slots or write both ABLs. Every write was followed by a full readback, not just a success message from the tool.

6. Verify root and persistence

Power on if needed and connect USB without holding the engineering button. The camera may still show its connected screen. That does not tell you whether ADB is available; check from the host: 

adb devices -l
adb shell id
adb shell cat /proc/cmdline
adb shell systemctl is-enabled adbd.service
adb shell systemctl is-active adbd.service

Our relevant results were:

uid=0(root) gid=0(root) ...
mp_state=engineering
androidboot.secure_debug=1
systemd.setenv="SLOT_SUFFIX=_b"
enabled
active

USB re-enumerated during startup; one early ADB command reported that the device was missing before the next attempt succeeded. Allow it to settle rather than treating a single transient disconnect as a reason to reflash. If ADB stays unavailable, check the host's USB permissions and the actual boot state. Do not try to fix it by flashing someone else's userdata.

Then check the bootloader itself and return to the normal system:

adb reboot bootloader
fastboot devices
fastboot getvar unlocked
fastboot getvar current-slot
fastboot getvar product

# Our output:
# unlocked: yes
# current-slot: b
# product: kalama

fastboot reboot
adb wait-for-device
adb shell id

Root ADB returned automatically after that reboot. We also verified that the data and media storage mounted, and checked the normal live view and touch controls after unplugging USB. The camera displayed a FactoryMode overlay, which we left in place. We did not establish full recording/playback, thermal, battery-life, or long-term stability equivalence with stock firmware; "we got root" is a narrower result.

Recovery and everyday use

Alliot's rollback path is to re-enter EDL, re-read GPT, restore this camera's original active ABL, verify its full readback, then restore the original devinfo and verify that too. Reset only after both comparisons pass. The commands use the same device-specific addresses as before, revalidated against the current GPT: 

edl ws "$ABL_START" "$ORIGINAL_ABL" --memory=ufs --lun="$ABL_LUN"
edl rs "$ABL_START" "$ABL_SECTORS" abl-restored.bin \
  --memory=ufs --lun="$ABL_LUN"
cmp abl-restored.bin "$ORIGINAL_ABL"

edl ws "$DEVINFO_START" "$ORIGINAL_DEVINFO" --memory=ufs --lun="$DEVINFO_LUN"
edl rs "$DEVINFO_START" "$DEVINFO_SECTORS" devinfo-restored.bin \
  --memory=ufs --lun="$DEVINFO_LUN"
cmp devinfo-restored.bin "$ORIGINAL_DEVINFO"
edl reset --resetmode=reset

We prepared the original images for recovery but did not exercise rollback after the successful root. Keep them, the verified loader, and the engineering cable. EDL recovery still depends on being able to enter EDL and communicate reliably with storage.

For normal use, simply connect USB and run adb shell. Root ADB now starts automatically, so only attach the camera to trusted hosts. Alliot notes that an OTA can replace the factory ABL and remove ADB; re-check the firmware, GPT, and active slot after an update rather than repeating old flash commands blindly.

The useful result here is a root shell while retaining the camera's existing system and userdata. Alliot supplied the method and verified binary hashes; our contribution was working through the English/Linux procedure and testing an active-slot-B camera with staged writes and readback checks.
